# Disclaimer
This document is not officially provided by the VDMA. It is a best effort summary of the most important changes between LIF version 1.0 and LIF version 2.0 by the LIF core workgroup. Trivial changes such as grammatical corrections are not included here.

Part or all of these changenotes and their described and referenced objects and section numbers or section names may become out of date upon any new release of the LIF, be it a major, minor, or patch version.

For a truly exhaustive changeset, you may git diff the appropriate LIF markdown versions against one another.

# Breaking Technical Changes (Both Small and Large)

## LIF ID Added to Metadata
New required property to explicitly identify the facility for which this LIF applies.

## New Near-Root Object: Origin
Previously: LIFs had Layouts. Now: LIFs have Origins which have Layouts. Two layouts sharing an origin explicitly confirms that the layouts share a coordinate origin (including rotation and scale) and that their coordinate systems are aligned, and therefore whether the two Layouts directly overlap and if so exactly how. See new section 8.3.3.1 Best Practices for Defining an Origin for more information.

## Removal of Node's Name Property
In LIF 1.0, nodes had names, IDs, and descriptions/descriptors, whereas VDA 5050 only ever had nodes with IDs and descriptions/descriptors. LIF 2.0 has removed node names entirely, leaving them with only IDs and descriptors. The inclusion of three descriptive/identifying fields in the LIF but only two in VDA 5050 was reported to cause significant confusion and friction.

## mobileRobotType[Node|Edge]Property Supports Multiple Types
The mobile robot type specific properties on nodes and edges now accept a collection of mobile robot types to where all of their properties apply. This allows for two separate mobile robot types to share properties instead of having to re-define an entire new mobileRobotType*Property for every different type of mobile robot on every single node and edge.

## Node and Edge Actions
Previously, each action had a `requirementType`, REQUIRED, CONDITIONAL, and OPTIONAL. There was no way for a LIF to declare any particular action type as forbidden. Feedback was clear: the distinction between CONDITIONAL and OPTIONAL was not, in practice, significant enough to matter, and some users of the LIF did not have their use-cases satisfied with what was in effect a requirement of strict whitelisting of actions on all nodes and edges.

On each mobileRobotType*Property object, instead of their simply being an actions collection, there are now three collections: `requiredActions`, `feasibleActions`, and `forbiddenActions`. Required actions speak for themselves; feasible actions are essentially a union of conditional and optional actions previously; and forbidden actions (or rather, just their type) likewise define exactly what one would imagine. See sections 8.3.6 or 8.3.13 for more information.

`requirementType` has therefore been removed from the action object.

## `rotationAllowed` -> `reachOrientationBeforeEntering`
This was also changed in VDA 5050 3.0. Naively for most cases: `reachOrientationBeforeEntering` is just the inverse of `rotationAllowed`. See the relevant descriptions in the LIF 2.0 and VDA 5050 3.0 for a complete breakdown.

## Edges with Multiple Orientations
Edges' `mobileRobotTypeEdgeProperty` used to support only a(n optional) single `vehicleOrientation`. Now, an optional collection of orientations, `vehicleOrientations`, may be defined. This potentially reduces the amount of edges (and potentially nodes) required to be defined between two physical points for forwards/backward movement as a side effect, but was especially useful for more exotic use-cases of omni-directional robots.

## Allowed Deviation
VDA 5050 3.0 introduced elliptical allowed deviations whereas in previous versions only circular ones were permitted; LIF 2.0 followed. (This is also an example of an object and its fields which has a backwards compatibility note, described below.)

## Nomenclature Updates to Align with VDA 5050 3.0
LIF 1.0 was created in the context of VDA 5050 2.0, mirroring its terminology wherever possible. LIF 2.0 has been created in the context of VDA 5050 3.0, and has done the same. Some examples (non-exhaustive):
- Most "Description" fields changed to "Descriptor" (all of the ones that VDA 5050 uses).
- "AGV", "AMR", and "Vehicle" now "mobile robot".
  - E.g., it is now "mobileRobotTypeEdgeProperty" instead of "vehicleTypeEdgeProperty".
- Abbreviations such as "max" expanded to full words such as "maximum".

# Other Changes and/or Additions

## Corridors
Corridors, introduced in VDA 5050 2.1, can now be defined in LIF 2.0.

## Removal of Uni-Directionality Constraint of LIF Transfers
The LIF no longer explicitly states that it is a vehicle provider to traffic control provider definition. It is now a party-agnostic mere declarative definition of the navigation graph which a mobile robot supports, and the information required by a traffic controller to supply VDA 5050 orders to the mobile robot. The text in section 7 has been updated accordingly.

This means that any party may create and supply a LIF to other parties, be they design tooling providers, mobile robot providers, fleet control providers, integrators, or whomever else.

## LIF 2.0's Support of Different VDA 5050 Versions
While LIF 2.0 has been changed in many ways (see some secondary changes below) to match VDA 5050 version 3.0's new nomenclature, fields, and so forth, backwards compatibility of LIF 2.0 with VDA 5050 2.1 was preserved. Some LIF fields have notes to a traffic control provider about which fields in the LIF, and how, can be used in a VDA 5050 2.1 context.

Whether LIF 2.0 (or even 1.0 for that matter) is compatible with earlier versions of VDA 5050 than 2.1 was not explored or considered. The LIF team will continue in the future, if able, to make reasonable attempts to keep future versions of the LIF as backwards compatible with older versions of VDA 5050 as is practical.

## `loadRestriction` Now Present on Nodes
Previously these were only available on edges. `loadRestriction`s are now also definable on nodes.

## Physical Line-Guided Mobile Robot Support
See new section 8.3.16 PhysicalLineGuidedProperty. Note that these are mutually exclusively definable with a trajectory definition on the same edge for the same mobile robot type(s).
